# 斷電恢復改版：板子上的驗證步驟

## 要換的檔案

第二版（review 後的修正）只改了三個 .c，header 沒變：

- `Core/Src/flash.c`：開機先等 flash 做完上一個操作；寫入、擦除送指令前先等
- `Core/Src/log.c`：換 sector 一律先擦；log 是空的時候先擦 S0；寫入或擦除失敗就停止寫入，remount 時重新判斷
- `Core/Src/log_uart.c`：kernel 還沒啟動時不拿 mutex

record 格式沒變，flash 上的資料不用重新 format（下面每個測試都會先 format）。

`(reset)` 的意思是按板子上的黑色 reset 鍵，`log remount` 也可以。

## 0. 燒新版之前（可選）：用目前的版本跑一次 F

目前的版本在 F 的最後會是 `[1] @0x002000 ... "first"`：S0 被跳過，寫一半的 header 留在 S0。新版是 `[1] @0x001000`。

## 1. 第一版：先用舊版跑一次 A

（第一版的步驟，留著當紀錄。）舊版在第二次重開後會變成：

```
[LOG ] init: 3 valid, 1 corrupt, wp=0x002000, next_id=4 oldest=S0 active=S1 (recovered)
...
  [4] @0x002000 len=4 ... crc=BAD
```

write pointer 又跳回 0x002000，`good` 被 `next` 疊寫，兩筆都壞了。第一版的 header 多了 CRC-16，舊格式的 record 會被當成壞掉，所以燒第一版之後要先 `log format`。

## A. 寫到一半 → 重開 → 寫一筆 → 再重開

```
log format
log write hello
log write world
log partial abcdefghij
(reset)
log write good
(reset)
log write next
log dump
```

預期：

- 第一次重開：`init: 2 valid, 1 corrupt, wp=0x002000 (full), next_id=4 oldest=S0 active=S0 (recovered)`
- 第二次重開：`init: 3 valid, 1 corrupt, wp=0x002018, next_id=5 oldest=S0 active=S1`
- dump：`[4] @0x002000 ... crc=OK "good"`、`[5] @0x002018 ... crc=OK "next"`

## B. 換 sector 時，PAD 寫完就斷電

```
log format
log fill 48 64
log padcut
(reset)
log write short
(reset)
log dump 47 5
```

預期：

- 重開：`init: 48 valid, 0 corrupt, wp=0x002000 (full), next_id=49 ... (recovered)`
- 再重開：`init: 49 valid, 0 corrupt, wp=0x002019, next_id=50 oldest=S0 active=S1`
- dump：`[49] @0x002000 len=5 ... crc=OK "short"`（改版前會把它疊寫在 0x001FC0 的 PAD 上）

## C. 下一個 sector 不是全 FF（模擬擦到一半）

```
log format
log fill 70 32
write 0x002000 garbage
log fill 20 32
log stats
log dump 76 5
```

預期：

- stats：`records=90 corrupt=0`，`erases=1`（跨進 S1 時先擦）
- dump：`[79] @0x002000 ... crc=OK`

## D. 剛好填滿 sector，並繞過一圈

```
log format
log fill 1100 44
log stats
(reset)
log stats
```

預期（44 B payload ＝ 64 B 一筆，每個 sector 剛好 64 筆）：

- 兩次 stats 都是 `records=972 corrupt=0 sectors=16/16 wp=0x002300 next_id=1101`、`oldest=S2 active=S1`
- 第一次 stats 的 `erases=17`：第二版換 sector 一律先擦，第一圈 S1–S15 擦 15 次，繞回來擦 S0、S1 兩次（第一版只有繞回來那 2 次）
- reset 之後 `erases=0`：這個數字只記這次開機
- 改版前在這裡 write pointer 會跑到 0x011000（log 區外面）

## E. header 寫到一半

```
log format
log write hello
log tornhdr
(reset)
log write after
(reset)
log dump
```

預期：

- 重開：`bad header @0x001019, skip rest of sector`，`init: 1 valid, 1 corrupt, wp=0x002000 (full), next_id=3 ... (recovered)`（讀不出那筆的編號，直接跳過一號）
- dump：`[1] "hello"`、`[?] @0x001019 bad header`、`[3] @0x002000 "after"`

## F. log 是空的時候，header 寫到一半（第二版新增）

```
log format
log tornhdr
(reset)
log write first
(reset)
log dump
```

預期：

- 重開：`init: 0 valid, 0 corrupt, wp=0x001000, next_id=1 oldest=S0 active=S0 (recovered)`
- 再重開：`init: 1 valid, 0 corrupt, wp=0x001019, next_id=2 oldest=S0 active=S0`
- dump：`[1] @0x001000 len=5 ... crc=OK "first"`：寫入前先把 S0 擦掉再用

## G. 擦除中途 reset：開機要等 flash 做完（第二版新增）

reset 鍵按住的時間（約 0.1～0.3 秒）比一次擦除（約 55 ms）還長，放開時 flash 早就擦完了，所以手按 reset 幾乎測不到。真正會出事的是 watchdog 這種瞬間的 reset。

`busyreset` 會擦一個用不到的 sector（0x100000），不等擦完就用軟體 reset，效果跟 watchdog 一樣。這個指令要換 `flash.c`、`flash.h`、`storage.h`、`cmd.c`、`main.c`。

```
log format
log fill 200 44
busyreset
log stats
```

預期：

- `[STOR] erase @0x100000, reset before it finishes`
- 開機先出現 `[FLSH] busy at boot, waited N ms`（N 大約幾十 ms），接著才是 `[LOG ] init: 200 valid, 0 corrupt, wp=0x004200, next_id=201 oldest=S0 active=S3`。改版前這時候 log_init 就直接去讀，讀到的不是 flash 裡真正的資料
- `log stats`：`records=200 corrupt=0`

## 時間欄位

`t=`、`last_append_us`、`init_us` 這些數字每次都不一樣，不用比對。
